## Assumptions (confirm on approval)
1. **Where it plugs in.** `merge_slice` / `Merge-Slice` of slice 05: when `git merge --squash` conflicts, the conflicted files are split into resolvable ones – `work/checklist.md` and the open round record, whose path is read *before* the merge (a conflict at its first line would hide `Status: open`) – and foreign ones. Any foreign file: `git reset --merge`, stop naming **only the foreign files**, resolve nothing. Otherwise each resolvable file is resolved, checked and staged, and the queue goes on with the Commit tick and `git commit -F` as before. Without an open round (`--merge` after the close) only the checklist is resolvable. Recommendation: yes.
2. **Checklist rule.** Built from the two committed versions, not from git's merged text: every line of `HEAD:work/checklist.md` in its order; a row whose slice number the branch also has gets the **union of ticks per column** (cells split at `|`; ☑ in a cell of either row makes that cell ☑); rows only on the integration branch stay; rows only on the branch are appended in the branch's order. Rows are matched by number the way `is_done` matches them. Then the Commit tick of slice 05 runs on the result. Recommendation: yes.
3. **Round-record rule.** git's merged text with markers: inside every hunk the integration branch's side first, the branch's side after it; the marker lines `<<<<<<<`, `=======`, `>>>>>>>` dropped, and the base section of the `diff3`/`zdiff3` styles (`|||||||` up to `=======`) dropped as well, because a target repository may set `merge.conflictStyle`. Text outside hunks is kept as git merged it. Recommendation: yes.
4. **The check, refined.** Before staging, both files: (a) no line starts with `<<<<<<<`, `=======`, `>>>>>>>` or `|||||||`; (b) the round record: every line that both sides kept, and every line that either side added against the merge base, occurs in the result; the number of lines starting with `Result:` equals ours plus theirs minus the merge base; (c) the checklist: every row number of both sides is there, and no ☑ of either side's row is missing from the result's row (union with the result changes nothing). The slice file says "every line of both sides occurs"; taken literally, a slice that edits an existing line of the record (for example removes an answered `NEEDS-DECISION:` line) would always fail, although nothing was lost – the refined rule keeps exactly what the literal one protects. The comparison ignores carriage returns (this machine checks out with CRLF). A failed check: `git reset --merge`, stop naming the file and "failed its check", branch kept. Recommendation: yes.
5. **No third runtime.** bash with its own tools (`read`, arrays, `grep -Fx -f`, `git show`, `git merge-base`) and PowerShell with .NET collections; scratch files for the line sets go to `.slice-loop/` (git-ignored). Both scripts get the same functions (bash `row_number`, `union_row`, `resolve_checklist`, `resolve_record`, `check_resolved`, `open_round_file`; PowerShell `Get-RowNumber`, `Merge-RowTicks`, `Resolve-Checklist`, `Resolve-Record`, `Test-Resolved`, `Get-OpenRoundFile`) and the same messages. `open_round` / `Get-OpenRound` are built on the new `…_file` helper, so the open-round rule stays in one place per script. Recommendation: yes.
6. **Tests** (`tests/loop_test.py`, vibe-coding profile; slice 05's harness): the fake claude appends `- Slice NN stub surprise` and a block `### Slice NN stub check` / `Result: ☐` to the open round record on every branch build (also for prepared branches; `STUB_RECORD_LINE` adds one more line); case expectations gain `record_has`, `results` (count of `Result:` lines in the record), `checklist_has` and `says_not`; prepared branches can be followed by a commit on `main` that adds a checklist row (`main_row`). The vibe-rebuild profile stays unchanged. Recommendation: yes.
7. **Docs.** CHANGELOG: the slice 05 bullet's sentence "Until rule-based resolution follows … stop at the second squash" is replaced by one bullet for the resolution (it would be false after this slice); script headers say which files are resolved by rule. READMEs are slice 07. Recommendation: yes.
8. **Not touched:** the `/slice` command (its section 4 step 6 already describes the same checklist for squashes by hand), `rebuild-loop.*`, slice-board. Recommendation: yes.
