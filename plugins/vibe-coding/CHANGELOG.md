# Changelog

## 1.9.0 – 2026-10-30
Shorter, from a review of the whole plugin: a slice session now loads about 240 lines instead of 350, and rules that came from single incidents no longer sit in every session's context.
- **`/slice` split by path.** Round close, parallel sessions and quick fixes move to `.claude/slice/close.md`, `parallel.md` and `quick.md`, read only for that argument; marker lines are section 5. `references/round-close.md` is now the one source of the close steps and the manual test block format. Refresh all copies in target repositories together.
- **Test guard.** No function may be defined twice in a loop script; `tests/loop_test.py` waits `LOOP_TEST_TIMEOUT` seconds per case (300).
- **Single-incident rules move to the `work/session-hints.md` template:** pipes hiding exit codes, leftover child processes, waiting for another session's build, recording raised timeouts.
- **Queue lock.** `.slice-loop/merge.lock` keeps two `-Merge` queues apart in one checkout: the second does nothing and exits 0; a lock older than 60 minutes counts as dead and is taken over.
- **Stricter decision lines.** A line under `## Decisions` must end in `– <who>, <date>`, as a repository that allows names writes it, too.
- **`.slice-loop/slice-NN.msg` is required.** The fallback message from name and source is gone; a slice without one is left behind.
- **Removed:** progress percentages and the tool table in the skill; about 45 wording tests and the rising line limit in `tests/markers_test.py`.

## 1.8.0 – 2026-10-30
More from round R05, after 1.7.0: two finished slices waited four hours because their reports never woke the orchestrating chat.
- **`-Merge -Watch` / `--merge --watch`.** Waits until a slice reports ready on a new tip, runs the queue once and exits, so a background run squashes without the chat and its end wakes the chat. A slice left behind (`.slice-loop/slice-NN.left`) brings it back only with a new tip; a second watch next to a running one (`.slice-loop/watch.alive`, under 60 minutes old) exits at once. `SLICE_WATCH_SECONDS` (60), `SLICE_WATCH_MAX` (480). `/slice` section 7 has the orchestrator start it after starting sessions. Both loop scripts.
- **Registration files and scaffolds.** `files` also names the shell, resource lists and route tables, and a slice that builds a scaffold others use lands first: two slices had been judged independent, then collided in four shared files with two scaffolds, and later pairs collided in the same files.
- **Session hints may be corrected.** A bullet that contradicts `work/conventions.md` or the current `/slice` is corrected; hints told sessions to repeat every check after a merge, against the check levels.
- **No answer to a turn end without a marker.** 30 `SLICE-WAIT` turns each drew a status report despite 1.7.0; the rule now says to end the turn without text, and sessions use the marker while a subagent runs too.
- **Superseded manual test steps** get "(superseded by slice NN: …)" on their Expected: line.
- **A filtered run without tests is no proof.** Two slices' filters selected nothing.
- **The closing report names leftovers.** Squashed slices whose worktree or folder could not be removed are listed at the end. Git drops its worktree entry even when files inside are held, so the retries stop there and the folder is named.

## 1.7.0 – 2026-10-30
More from round R05: the merge queue and the orchestrating chat caused work and reports nobody needed.
- **"Not ready yet" no longer fails `-Merge`.** A slice whose session has not written `.slice-loop/slice-NN.ready` for its tip (it is still checking) is listed as "not ready yet" and the queue exits 0 for it; a non-zero exit now means a real problem – a conflict, a missing or red proof, a malformed record, a lost link target. In the build loop, where the session has ended, a missing ready file still leaves the slice behind. Both loop scripts.
- **No re-merge after every squash.** `/slice` section 4, step 6a merges the integration branch into the slice only when `git merge-tree --write-tree` reports a conflict or the integration branch changed a file the slice also changes (documents `*.md` and `work/` aside); otherwise the slice keeps its tip and its proof. The queue squashes a slice cut from an older integration branch as it is, and leaves it behind with "integration branch moved and touches <files> – merge it on the slice branch" when the two overlap, conflict or not; a real conflict in a document says to merge on the slice branch, too.
- **One decision format per kind.** Under `## Decisions` of the round record a line is either `Ruling: <decision> – User, <date>` (the user's answers) or `Build decision (slice NN): <decision> – Claude, <date>` (what the session decided while building); the slice command and the record template say so, and the queue refuses a slice that adds a line in another format there (a leading `- ` is allowed).
- **Fewer interim reports.** In `auto` and `parallel` mode a slice session reports only through its markers: the orchestrating session reacts only to `SLICE-READY`, `NEEDS-DECISION` and `SLICE-OPEN`. "Suite still running" is no report; `SLICE-WAIT` is one line without status text, used only when the harness ends the turn while checks still run, and needs no answer.

## 1.6.0 – 2026-10-30
Lessons from round R05 of a target repository: three parallel slices. Every squash made the other slices merge the integration branch and rerun every full suite (desktop about 18 minutes, API about 13 under load), load turned unrelated tests red, and the full-suite lock serialised everything, so slices took hours.
- **Check levels 1–5, default 3.** A new line `- Check level` in `work/conventions.md` decides how often and how thoroughly a slice is checked; the round record may set another level and name its milestones under Decisions, and a slice may set its own with the new `_slices.json` field `check_level` (rendered as "Check level" / "Prüfstufe" in the slice file). 1: own checks without scan tests, no full suite in the slice. 2: own checks with scan tests, the full suite of an area only when the slice touches shared code (shared controls, styles, shell, middleware, database triggers, a new rule on an endpoint, service or base class). 3: like 2, plus `slice-loop -Merge -Verify` at the round's milestones and at round close instead of after every group. 4: like 3, plus `-Merge -Verify` after every group and, after merging the integration branch, the full suites of the areas it changed since the old base. 5: the full check chain in every slice and after every merge of the integration branch. The levels are defined in `/slice` section 4, step 1; `/slice status` shows the level and the next milestone; intake names the milestones.
- **Targeted re-check after merging the integration branch.** Section 4, step 6a notes the old base, then repeats the baseline and the slice's own checks; full suites run only when the level asks or `git diff --name-only <old base> <integration branch>` lists a file the slice also changes. A test red under load is re-run alone first; the whole suite only when it stays red.
- **At most two parallel slices by default** instead of three: `/slice` section 7 suggests two, `slice-loop -Parallel` / `--parallel` defaults to `SLICE_PARALLEL_MAX=2`, and slice-board offers two slots. Three sessions on one machine made unrelated tests red under load and queued at the full-suite lock.

## 1.5.1 – 2026-10-28
- **The keys of `work/conventions.md` stay English.** An intake in German had written „Basisprüfung“ and „Volle Prüfkette“ instead of `- Baseline check` and `- Full check chain`. The loop scripts read only the English keys, so the merge queue silently stopped requiring the baseline commands in the checks proof, and `-Merge -Verify` would have found no chain. Both loop scripts report a `work/conventions.md` without a `- Baseline check` line at their start, and `-Verify` names the missing `- Full check chain` key.

## 1.5.0 – 2026-10-28
Lessons from round R04 of a target repository (ten slices in parallel sessions).
- **`SLICE-READY` is bound to the branch tip.** The merge queue squashed two slices while their last checks still ran and removed their worktrees under them: format and build were already green on the tip, the tests were still running, and a squash message of an earlier pass was there. `/slice` now writes the tip's SHA to `.slice-loop/slice-NN.ready` as its very last write before `SLICE-READY`, and again after any later commit or merge. Both loop scripts squash only a slice whose ready file names its tip; otherwise it is left behind with "not reported ready" or "moved after SLICE-READY". Copy the command and the scripts together: a 1.4 `/slice` writes no ready file.
- **One last checks run.** The run that proves the slice comes after the tick, the protocol entries and the merge of the integration branch, on the final tip; a slice ran its 35-minute chain twice before. The merge step appends to the checks proof instead of rewriting it.
- **Red is recorded.** The red run goes into the checks proof with its exit code and SHA, and Tests red is ticked only with such a line – three slices had written test and code in one go.
- **Baseline in the worktree.** The baseline check runs in the slice's fresh worktree before the first change; in the main checkout a build picked up half-done files of other slices' worktrees.
- **Build rules.** Screen behaviour is tested through real input (a click path was broken while a view-model test was green); generated outputs the change does not explain are reset (113 unrelated screenshots); stopping a background check leaves its child processes running, so they are found by the worktree path and ended.
- **Fresh reviewer.** The review is a read-only pass over the whole branch diff by a subagent that did not write the code; in R04 it found real faults in three slices.

## 1.4.0 – 2026-10-27
Lessons from round R03 of a target repository: 24 points, collected while an orchestrating chat ran the slices in parallel sessions.
- **The orchestrator runs on Opus at low effort.** A session cannot start a session on a stronger model than its own – the harness silently falls back (two `opus` slices started on Sonnet). A chat that only dispatches and squashes now runs on `opus` at low effort (`claude --model opus --effort low`) instead of a cheaper model, checks each started session's model and switches it when it differs. The start brief carries a background text and, for repositories with a fact-forcing hook, the facts it asks before the first command.
- **A hard list before `SLICE-READY`.** Ticked through Checks, `.slice-loop/slice-NN.msg` written, a green proof line on the branch tip for every check and baseline command, everything committed – checked one by one, since a session that skipped them was only caught at the squash. A turn that ends while anything runs in the background ends with `SLICE-WAIT`, never with a plain "I wait for …".
- **Checks proof survives stale runs.** The proof is appended to; the queue reads only the lines with the branch tip, the last one per command, and ignores the rest (an orphaned test run of an old session had overwritten a slice's proof).
- **Files per slice.** `_slices.json` entries carry `files` – the paths or folder prefixes a slice expects to change, rendered as "Files expected to change". `/slice status` shows "Ready now" with the slices that share a path, `/slice` offers them one after the other, and `slice-loop -Parallel` keeps them out of one batch and starts at most three slices at once (`SLICE_PARALLEL_MAX`).
- **`-Merge -Verify`.** After the queue squashed at least one slice it runs the full check chain of `work/conventions.md` on the integration branch under the full-suite lock; the orchestrator runs it after each group.
- **Queue safety.** The entries behind each link in a worktree (a `node_modules` junction) are counted before and after its removal and a loss is reported; the removal is retried with the write backoff while a shell still stands in the worktree; a stale full-suite lock whose slice branch is gone is reported with the command to remove it; a squash that would glue two lines of the round record into one is refused; "already squashed, but moved since" now says that there is nothing to do.
- **Wider check scope and a strict red.** Red means the test fails against the code before the change (stash or a second worktree), not against a wrong expectation. A new rule on an endpoint, service or base class runs the tests of every caller or the full suite; a shared control runs its own tests first; key bindings, focus or tab order add the focus-order tests. A load-only failure is noted as "load, not a fault".
- **Foreign builds.** Generated files another session's build changes in the shared checkout are waited out (at most 10 minutes) before the clean-tree check, and left alone.
- **`/slice quick <finding>`.** A short path for a fix outside a slice, for example after the round is closed: finding in `work/quick-fixes.md`, failing test first, full check chain, one commit, protocol entry, `QUICK-DONE: <sha>`; the next intake reads the file.
- **Round close cleans up.** `/slice close` lists leftover worktrees and `slice-*`, `agent-*`, `worktree-*` branches with their tip SHA and offers to remove those without changes, links first.

## 1.3.1 – 2026-10-26
- **A file another process holds no longer stops the merge queue mid-squash.** In the first round with 1.3.0 a scanner or indexer twice had a resolved ~930 KB markdown file mapped (Windows ERROR_USER_MAPPED_FILE); `slice-loop.ps1 -Merge` died on the write and left the main checkout mid-squash (`UU` files, `.git/SQUASH_MSG`). Both loop scripts now retry every write of the merge queue and every reset of a merge (`SLICE_WRITE_RETRIES`, default 5; `SLICE_WRITE_BACKOFF_SECONDS`, default 2). A file still held after the last retry leaves that slice behind – `slice NN: could not write <file> (locked by another process) – merge reset`, branch kept – and the queue goes on with the next one (exit 1 at the end, as for any slice left behind). Any other way out of a squash – an exception, a stop, a signal – resets the merge (PowerShell `try`/`finally`, bash an `EXIT` trap); the reset is `git reset --hard`, as the queue starts every squash on a clean checkout and a `reset --merge` that failed half-way leaves files every later `reset --merge` refuses. Only a reset that still fails after its retries stops the loop, and it says so. Tests: three cases per shell in `tests/loop_test.py` – a write retried until the file is free, a file that stays held (the slice is left behind, the reset retried while the checklist is held, the next slice squashed) and a refused squash commit that leaves a clean checkout; the test maps the file as a scanner does on Windows and makes its folder read-only elsewhere.

## 1.3.0 – 2026-10-26
Lessons from round R02 of a target repository: 27 slices in parallel sessions plus the merge queue.
- **The merge queue resolves append-only conflicts in any text file.** A conflict hunk whose diff3 base is empty – both sides only added lines at the same place, such as two entries at the end of the decision protocol or two new findings – keeps the integration branch's lines, then the slice's, and the check confirms that every line of both sides is there. A hunk whose base is not empty is a real conflict and stops that slice; the open round record keeps its rule of 1.2 (both sides). Both loop scripts.
- **The round's status row is merged by rule.** A hunk of table rows where both sides changed rows with the same key (first cell) and no side removed one becomes one row per key: a cell only one side changed takes that change, a cell both changed keeps the integration branch's text and adds the `; `-separated items only the slice has (`| R02 | open | Slice 03 done; Slice 12 done |`). The check requires every item a side added and no more rows per key than either side had, so parallel squashes no longer create duplicate rows.
- **A conflicting slice no longer stops the queue.** The queue resets that merge, keeps the branch, goes on with the next slice and at the end lists every slice left behind with its reason (conflicting files, failed check, missing proof, duplicate id, malformed test block); it exits non-zero when one was left. The build loop treats a left slice like a blocked one and stops with the list when nothing else is ready, without closing the round.
- **Proof of checks before the squash.** `/slice` writes `.slice-loop/slice-NN.checks` in the main checkout – one line `<exit code> <commit SHA> <command>` per check it ran (section 4, steps 1, 5 and 6a; rewritten after merging the integration branch). The queue squashes only when the file exists, every exit code is 0, every SHA is the branch tip and every command of the `Baseline check` line of `work/conventions.md` (its backtick spans before the arrow) is listed; otherwise it leaves the slice and says why.
- **Unique finding ids across parallel slices.** Slices get a reserved range for new findings (`ids` in `_slices.json`, rendered as "Ids for new findings", and a `New ids` column in `## Slices`); without one `/slice` reads the ids in use on the integration branch and renumbers its own on a collision. The queue refuses to squash when an id would be defined twice – as the first cell of two table rows or the first word of two headings – in the round record or the findings file named in backticks under `## Source` (ids already doubled on the integration branch do not count). An id is uppercase letters, an optional `-` and digits; the letters may be non-ASCII capitals (`Ä77`): PowerShell matches `\p{Lu}`, bash matches A–Z and the UTF-8 Latin-1 capitals À–Þ byte-wise (`LC_ALL=C`).
- **Manual test list in one format.** `/slice` inserts its block in slice-number order: steps `1.`–`n.`, exactly one `Expected:` per step, exactly one `Closes:` and one `Result: ☐` per block. The queue keeps the blocks in slice order after a resolution and refuses a slice whose own block breaks the format; `/slice close` validates every block and ends with `ROUND-OPEN: Rnn manual test list: …` instead of repairing silently.
- **Waiting is not done.** A slice session that ends its turn while checks still run prints `SLICE-WAIT: NN <what runs>` (marker list, section 6); the loop scripts count it as still running and check back in the same session (`SLICE_WAIT_SECONDS`, default 60; `SLICE_WAIT_MAX`, default 30 check-backs).
- **Worktree leftovers.** When the queue cannot remove a worktree it names the likely cause – a shell, editor or process inside it, or a lock – and keeps worktree and branch; a later `-Merge` / `--merge` retries the removal (after unlinking links, as in 1.2.1) when the branch still points where it did at the squash (`.slice-loop/slice-NN.squashed`).
- **Open decisions stay open decisions.** Every question for the user is a `NEEDS-DECISION:` line under `## Open decisions`, never only a note under deferred minors; `/slice close` also lists phrases outside that section such as "user decides", "<Name> entscheidet" or "decision pending".
- **New findings go into the findings file.** A slice adds the findings it discovers to the tracked findings file named under `## Source`, in its format and with an id from its range, so marking "done in slice NN" stays uniform.
- **Collect mode.** When the user collects points first ("ich sammle", "I'll say done"), the skill writes each one at once as a row of `work/_raw/intake-Rnn.md` and moves them into the round record's intake on "done" / "fertig".
- **Short parallel prompts, cheap orchestrator, headless long runs.** Section 7 prescribes `/slice NN parallel auto` plus goal and acceptance cases; the command reads conventions and session hints itself. The skill recommends a cheaper model for a session that only dispatches and squashes, and `slice-loop -Yes -Parallel` for long autonomous runs, since a desktop harness may refuse to start sessions from background events.
- **Test rules.** A raised timeout or wait in a test is recorded with its reason in the protocol entry, and the review checks for it; the conventions template has a line for test worker limits under load (for example a full Vitest run with `--maxWorkers=3`).
- **Tests.** `tests/loop_test.py` gains fourteen cases per shell and reworks one (a finding id with a non-ASCII capital, append-only lines in a foreign file, the status row, a real conflict left behind while the next slice is squashed – the former "stops on a foreign conflict" case, since two slices that create the same file only add lines now –, missing / red / stale / incomplete checks proofs, a duplicate finding id, manual test blocks in slice order, a malformed block, a parallel run that goes on past a left slice, `SLICE-WAIT` checked back on and capped, a locked worktree removed by a later `--merge`); the fake `/slice` now writes the checks proof and well-formed manual test blocks. `tests/render_slices_test.py` covers the `ids` field; `tests/markers_test.py` covers the new contracts of the command, the references and the skill.

## 1.2.1 – 2026-10-26
- **The merge queue no longer empties the target of a linked folder.** On Windows `git worktree remove` follows a junction inside the worktree (for example `node_modules` linked onto the main checkout) and deletes the target's content. Both loop scripts now remove every symlink and junction in the slice's worktree first, never what it points to: PowerShell deletes the reparse points, bash uses `cmd /c rmdir` on Windows (plain `/c`: the script turns Git Bash path conversion off, so `//c` would reach cmd as it is) and `rm` elsewhere. Test first: `tests/loop_test.py` gets a case whose fake slice links `node_modules` into its worktree; the main checkout's `node_modules/keep.txt` must survive the squash (red in both shells before the fix, 58 of 58 green after).

The command grew by 16 lines. Tests: `tests/markers_test.py` (`test_command_names_the_rule_terms` and six rule-group tests, `test_command_stays_short_and_positive`).

Tests: `tests/markers_test.py` (`test_templates_hold_session_hints_section`, `test_skill_creates_and_lists_session_hints`, `test_command_reads_session_hints_and_names_it_in_parallel_prompts`, `test_conventions_template_splits_the_check_scope`, `test_tracked_findings_file_is_marked_by_each_slice`).
- **`SLICE-READY: NN` marker and the `parallel` argument.** `references/slice-command.md` takes `[auto | parallel]`: such a run does the re-check after merging the integration branch, writes the squash message to `.slice-loop/slice-NN.msg` in the main checkout, does not merge, leaves Commit at ☐ and ends with `SLICE-READY: NN` (branch committed, checklist ticked through Checks, squash message written; waits for the merge queue); a run without both arguments squashes itself as before. `/slice status` shows "ready to merge" for such a branch, and the parallel prompts start with `/slice NN parallel` and name the merge queue. The loop scripts read the marker from slice 05 on. The command grew by 6 lines (214 → 220, the limit of its size test). Tests: `tests/markers_test.py` (`test_command_defines_every_marker` and five new tests).
- **Full-suite lock.** `references/slice-command.md` takes `.slice-loop/full-suite.lock/` in the main checkout before a full suite (`mkdir`, or `New-Item -ItemType Directory` without `-Force` in PowerShell; an `owner` file with `slice NN` and an ISO-8601 time), releases it right after the suite, red or green, waits and retries every minute (at most 30 minutes) while a live slice younger than 60 minutes holds it, and reports any other lock (`SLICE-OPEN: NN lock held by slice MM since <time>` in `auto`) without touching it. `/slice status` shows a held lock; the conventions template's "never two full suites at once" points to the lock, and SKILL.md lists it among the local files. The command's size limit moved from 220 to 230 lines. Tests: `tests/markers_test.py` (four new tests).
- **Merge queue in both loop scripts.** `slice-loop.sh` and `slice-loop.ps1` accept `SLICE-READY: NN` besides `SLICE-DONE: NN` and squash a ready branch in the main checkout themselves: clean tree, `git merge --squash slice-NN`, the Commit column ticked, `git commit -F .slice-loop/slice-NN.msg` (without that file, `Slice NN: <name> (<source>)` from `work/_slices.json`, also passed with `-F`), then the merged worktree and branch are removed (`git worktree remove` without `--force`, `git branch -D`, because git never counts a squashed branch as merged). Any conflict resets the merge, keeps the branch and stops with the conflicted files named. Parallel builds are squashed one after another in the order of the ready list. `--merge` / `-Merge` runs the queue alone – every `slice-NN` branch whose row on the branch is ticked through Checks, lowest number first – without a session or an open round. Tests: `tests/loop_test.py` runs the vibe-coding profile in a real git repository, with the fake claude building on its own branch and worktree (nine new or changed cases per shell: the queue for sequential, three-digit and parallel runs, ready but not ticked, `SLICE-DONE` still accepted, the fallback message, and three `--merge` cases); `tests/markers_test.py` requires `SLICE-READY:`, the merge option and `commit -q -F` in both scripts.
- **Rule-based resolution of checklist and round record.** When the queue's squash conflicts only in `work/checklist.md` and the open round record, both loop scripts resolve them by rule instead of stopping: the checklist is rebuilt from both committed versions (the integration branch's lines, the union of ticks per column for a row both have, rows only the branch has appended); in the record every conflict hunk keeps the integration branch's side, then the branch's side. The squash runs with `merge.conflictStyle=diff3`, because the default style moves lines both sides end with – such as `Result: ☐` – out of the hunk, and one of them would be lost. Before staging, a check stops and resets the merge when a conflict marker is left, a row or tick of either side is missing from the checklist, a line both sides kept or either side added is missing from the record, or the `Result:` lines do not add up to ours plus theirs minus the merge base. A conflict in any other file still stops the loop and names only those files. Tests: `tests/loop_test.py` (the fake claude appends a surprise and a manual-test block to the record on every build; two parallel slices now land both and close the round; a row only the integration branch has is kept; a foreign conflict names only the foreign file; a resolution that fails its check stops).
- **Release 1.2.0.** `plugin.json` and `SKILL.md` carry `1.2.0`; `README.md` documents `/slice NN parallel`, `-Merge` / `--merge`, the `SLICE-READY:` marker, the merge queue, the full-suite lock, the session hints and the check scope, and the root README names the merge-queue cases of the loop test and the new contracts of the markers test. The marketplace validation in CI (`.github/workflows/validate.yml`) and in the check chain runs without `--strict`, because `slice-board` carries no `version` on purpose (every commit is an update); both plugins stay strictly validated. Tests: `tests/markers_test.py` (`test_release_version_is_consistent`, `test_plugin_readme_documents_the_round_features`, `test_root_readme_names_the_merge_queue_cases`).

## 1.1.0 – 2026-10-25
- **Every slice runs on its own model.** `work/_slices.json` entries carry `model`: the cheapest model tier that does the slice reliably (`haiku`, `sonnet`, `opus`; tiers in `references/intake.md`), chosen per slice when the round is sliced, never inherited from the session that plans the round or starts the slice. The renderer prints it in the slice file, the loop scripts pass it as `claude --model` on every turn of the slice (a slice without the field runs on the CLI default), `/slice status` shows it, and `/slice` starts parallel sessions on it or heads each ready-to-paste prompt with `claude --model <model>`. Inside a slice, subagents run on that model or a cheaper one; only a reviewing pass may be stronger, and only when `work/conventions.md` asks for it. ## 1.0.0 – 2026-10-24
First version: turns findings lists and feature ideas into rounds of vertical slices and runs them one per fresh Claude session, in the way of [vibe-rebuild](../vibe-rebuild/README.md) but for everyday coding in any repository.
- **Rounds from findings lists or ideas.** Intake A takes a findings list (a tracked file, or the user's test notes in chat) into an intake table with ids that continue the repository's own scheme (`reopens <id>` when an earlier fix did not hold); intake B sharpens an idea into a brief of at most one page with Given/When/Then acceptance criteria (`superpowers:brainstorming` when installed, otherwise up to five questions). Ceremony scales with size; research (three short passes, licences included) runs only for technology or packages the repository does not use yet. Open decisions become `NEEDS-DECISION:` lines and carry over to the next round.
- **`work/conventions.md` honours the repository.** Discovered once from `CLAUDE.md`, `AGENTS.md`, README, working-method and protocol documents, CI, formatter configuration and `git log`: pointers with their source, never copies; conflicts between documents are listed, not resolved; `CLAUDE.md` is created only where none exists.
- **Slices** with Given/When/Then acceptance cases, patterns to mirror (`file:line`), NOT building, manual check items, a self-contained prompt and a Definition of Done; rendered from `work/_slices.json` by `render_slices.py` (`--lang en|de`). Slice numbers continue across rounds, also after a vibe-rebuild repository.
- **`/slice`** project command with `status`, `NN` and `close` (plus `plan`, `auto`, `direct`): baseline check first, plan with assumptions and review focus, tests first, one squash commit per slice on the integration branch, the repository's own protocol entry and "must change with a change" documents in the same commit. Never pushes. When two or more slices are ready, `status`, the next-slice run and the close of a slice offer one separate session per ready slice (never in `auto`; at most four suggested; ready-to-paste prompts where the harness cannot start sessions).
- **`slice-loop`** (PowerShell and bash): every slice in a fresh headless session, plan approval by Enter, text or `q`; `-Yes`/`--yes`, `-Parallel`/`--parallel`, `-DryRun`/`--dry-run` and `-MaxSlices N`/`--max-slices N`; closes the round with `/slice close auto` after the last slice; `SLICE_PERMISSION_MODE` for the permission mode.
- **Manual test list and round close.** `/slice close` runs the full check chain, writes the manual test list (start command, steps, expected result, finding ids, `Result: ☐` per slice) into the round record, sets `Status: closed` and commits it; the user's notes on the list are the findings list of the next round.
- **Tests.** `tests/markers_test.py` (command, loop scripts and templates agree on markers and formats), `tests/render_slices_test.py` (renderer), and `tests/loop_test.py` (both loop scripts of both plugins against a fake `claude` CLI, including `--max-slices`, round close and a three-digit slice number).
- **Relationship to vibe-rebuild.** Same formats (`_slices.json`, `checklist.md`, marker lines, two-run plan approval); vibe-rebuild is untouched. A repository finished with vibe-rebuild continues here with slice numbers after its last slice.
- **Name.** Other skills named `vibe-coding` exist elsewhere; they are methodology skills about how to prompt. This one runs the work, and the command written into your repository is `/slice`, so it cannot clash with them. Call the skill explicitly as `/vibe-coding:vibe-coding <file or idea>`.
